# services

Billboard's backend code: 48 AWS Lambda handlers in TypeScript, bundled with esbuild for the Node.js 24 runtime.
They fetch bills and members of Congress from congress.gov, summarize bills with Amazon Bedrock, serve the iOS app's
API, check sign-ups and send push notifications. The infrastructure that runs them is in `../infra`; the wire
contracts are in `../contracts`.

## Handlers

One directory per handler under `src/handlers/<name>/` (`index.ts` exports `handler`). Each is deployed as the Lambda
function named in the table, always invoked through its `prod` alias. Trigger and stack come from the synthesized
templates (`npm run synth` at the repository root).

### API (API Gateway `UserApi`, stage `prod`)

All in `UserAPIServiceStack`. "Cognito" means a Cognito user-pool ID token in `Authorization`; the user id is the
token's `sub`. Routes marked "body" validate that the request body is a JSON object. The route and auth table for
the whole API is in `../infra/README.md`.

## Pipelines

**Bills.** `billsApiPoller` → `UpdatedBillsQueue` → `fetchRawBill` → `raw-bills/` (S3) → `BillDifferQueue` (also via
`enrichOfficialVotes`) → `billDiffer` → `BillSummarizerQueue` → `billSummarizer` → `processed-bills/` (S3) → S3 event
→ `BillsManifestQueue` → `createBillsManifest` → `BillsManifest` (DynamoDB), then `NotificationTypeQueue` and
`CongressMemberStatsQueue`.

**Bills manifest snapshot (CAP-01).** `publishBillsManifest` (every 10 minutes) → `BillsManifest` and `BillPriority` →
`bills/manifest-v1.json` (gzip JSON) in the snapshot bucket. The app calls `GET /bills-manifest?delivery=snapshot`,
gets a 5-minute presigned URL from `fetchBillsManifest` and downloads the snapshot from S3 without an
`Authorization` header; incremental syncs (`updatedAfter`) stay inline. The presigned URL carries a session token:
it is a bearer credential, so never log it.

**Notifications.** `notificationType` → `userMatcherQueue` → `userMatcher` → `notificationFanoutQueue` (100 users
per message) → `notificationFanout` → `PendingNotificationsTable` → `notificationDispatcher` (every 5 minutes) →
`userNotifierQueue` → `userNotifier` → SNS → APNs. The pending-user markers the dispatcher reads are spread over
`DISPATCH_SHARD_COUNT` (8) partitions, `__dispatch__#<n>` with n from a SHA-256 of the user id
(`src/shared/dispatchShards.ts`). Every function that reads or writes markers must get the same count, and it may
only ever be raised (`../docs/RUNBOOK.md`, section 11).

| Type | When | Who gets it |
|---|---|---|
| `new` | No previous version of the processed bill | Users subscribed to one of its categories, life areas, sponsors or cosponsors; nobody for a ceremonial resolution (S6, `src/shared/commemorativeResolutions.ts`) |
| `updated` | The bill breakdown or "so what" changed | The bill's voters and watchers (a `Bill` or `Watch` row on it) |
| `alert` | The title or the actions changed; not when every new action is a vote the previous version already recorded in the same plain words on the same day (the coded line after the House's floor line of a failed suspension vote, or after the Senate's own line of a failed 60-vote vote: REL-50; a law line after another of the same day, REL-44), nor when the actions differ only by Congressional Record citations added, changed or removed (project decision 2026-11-12: a line that takes the place of one differing from it only by the citations at its end is not new, one line for one, `newBillActions` in `src/shared/billOutcomes.ts`, so a step repeated that day still is; the alert names a new action, never a line that only gained a citation; `../docs/RUNBOOK.md` 18.1). A bill becoming law has no type of its own: its law lines are an `alert` that says "Became law" | The bill's voters and watchers |
| `passed` | A new passage action (codes 8000, 17000; a passage line that only gained, changed or lost a Congressional Record citation is not new, 2026-11-12), unless the bill is a law (REL-44: a version that brings the passage with the law lines, or a passage line after them, is only the `alert`) | As for `new`, and the bill's voters and watchers (UX-33), in the news too. The same change's `alert` is written beside it for the alert's audience, and each device gets one of the two. For a ceremonial resolution no follower of its topics or life areas (S6, 2026-10-29): its voters, watchers and the followers of its sponsors and cosponsors |
| `failed` | A new failure of the bill itself (REL-50, `src/shared/billOutcomes.ts`): codes 9000, 18000, 33000 and 35000 only (a failure line that only gained, changed or lost a Congressional Record citation is not new, 2026-11-12); never an amendment, a motion (a failed suspension vote included), cloture, a conference report, a point of order, a failed Senate vote under a 60-vote order, an action with any other code or none (those are an `alert`); and not again for a bill whose previous version's actions already give `Failed`, nor for a law (REL-44) | As for `passed` |

While companion groups are on (APPF-23), three of these change for a bill in a pair: a user gets one `new` per pair (a
bill's `new` skips the users the other bill's `new` already reached, as that `new`'s own dedupe markers show, when the
other bill's manifest row has an older `updatedAt`, or on a tie for the Senate bill; after those markers' 3 days both
go out), and `alert`, `passed` and `failed` also reach the other bill's voters and watchers, each user once. `updated`
stays per bill.

One update can produce several types (a passage is both `alert` and `passed`; each device gets one of those two,
UX-33). While a bill is an active priority bill in `BillPriority` ("in the news"), its `new` goes to every active user
(but for a ceremonial resolution), its `alert` and `updated` to its voters, watchers and topic followers, and its
`passed` and `failed` to the same people as any bill's (UX-33). Each type's audience is one rule in
`src/shared/pushAudience.ts`. Every push applies the bill types the user chose, a bill in the news included, but never
to the bill's own voters and watchers. A passage
usually arrives as an action-only change, so `billDiffer` patches it into the processed bill without Bedrock, and that
write starts the notification path.

**What a push says, and when (S4, S5).** The action `notificationType` found for an `alert`, `passed` or `failed`
travels with the bill's first topic to the pending row, and the push names it: `Action: <title>` / `Reported by the
Committee on Energy and Commerce · Oct 27`, `Passed: <title>` / `Passed the House · Oct 27`, `Action: <title>` /
`Became law · Oct 27` for a law line (REL-44) (`src/handlers/userNotifier/pushCopy.ts`). Rows of one type keep it when several make one push ("2 Bills Changed" is
`updated`; several bills' actions stay a `digest`, since both apps read an `alert` push as one bill), and `updated`
rows go on a push of their own that lists every bill (up to 50 a push), so both apps ask to vote again on each. The
payload adds `category`, `subCategory` and, for one bill, `alert` (`text`, `actionDate`, `actionCode`), which apps 1.1
and 1.2 read for their Recent actions rows. No push goes out from 9 PM to 8 AM in the user's zone, from the state of
their district (`src/shared/quietHours.ts`; Eastern time when unknown): `userNotifier` holds the rows and extends the
dispatcher's claim to 8 AM, and the first dispatch after it sends them. A user gets at most one push every 3 hours
(UX-33, `src/shared/pushPace.ts`): rows that arrive inside the window are held the same way and folded into the next
push, `updated` rows keeping a push of their own (silent when it goes out beside another); and an `updated` row is
dropped unsent when the user voted on the bill after its summary changed. `../docs/RUNBOOK.md`, section 18.

**Votes and stats.** `setFeedback` (App Attest check, then the daily counter on `UserPII`) → `UserFeedback` → stream

**Verification and the vote re-stamp (INT-03).** `districtVerification` → `VerifiedAddressClaims` and `UserPII`;

**Sign-up (INT-05, INT-04).** Cognito `SignUp` → `preSignUp` (`PreSignUpCheck`) → `SignUpEmailClaims`, and
`AppAttest` when the app sends an assertion. CB-07: `signUpFilterCheck` makes the same `SignUp` call daily for the
check address and a +tag of it, with the probe token in its `ClientMetadata`; `preSignUp` labels those sign-ups as
probes (`SignUpProbeHit`, `SignUpProbeRejected`, the `probe` log key and a `PROBE#base` or `PROBE#variant` record in

ordinary one. App Attest itself: R2 → `POST /app-attest/challenge` and
`/app-attest/attest` (`appAttest`) → `AppAttest`; then its votes carry an assertion that `setFeedback` checks.

**Member stats (CAP-05).** `createBillsManifest` → `CongressMemberStatsQueue` (processed-bill key and `versionId`) →
`congressMemberStats` → `CongressMembersStats`, `CongressMemberVoteProfiles`, `CongressMemberLegislativeProfiles`.
While `MEMBER_STATS_RAW_BILL_TRIGGER` is on, `raw-bills/` writes also reach the queue through an S3 event; both paths
share the counted-guid guard, so a bill counts once per member on a row that has its counted-bill sets. A row counted
before the sets existed (every production row before this release) has a count and no set, and is never incremented:
it cannot tell which bills it already holds. `npm run backfill:congress-member-stats` rewrites the counts and seeds the
sets, and must run right after the first deploy (UA-03); until it does, existing members' counts pause, and each held
back increment is logged and counted as `MemberCounterSkippedUnseeded` (`BillBoard/CongressMemberStats`, an
embedded-metric log line).

Counters count the 119th Congress only (`COUNTED_CONGRESS`, a code constant): the apps label them "119th Congress". A bill
of another Congress is logged, counted as `MemberCounterOtherCongress` and changes no counter; its vote and legislative
profile rows are written as usual (REL-46). So a member new in the 120th Congress never gets a `CongressMembersStats`
row, and the two member APIs send no tracked counts for a member without one (project decision D8): the apps then show no
"Tracked by Billboard" section, rather than 0 and 0.

**Weekly digests (CAP-03).** `generateWeeklyDigests` (Sundays 10:00 New York) → `WeeklyDigestQueue` (25 users per
message) → `weeklyDigestWorker` → `UserWeeklyDigests` → `fetchLatestWeeklyDigest`. `src/shared/weeklyDigestBuilder.ts`

their bills, a decided bill the reader voted on is not in "Needs attention", and ceremonial resolutions never count
as topic matches (RUNBOOK 11.4 has the rules). Snapshots expire 21 days after publication; only the current week's is
read.

**Companion bills (APPF-23).** Identical bills introduced in both chambers (H.R. 1285 and S. 570) are paired so the
app shows them as one bill and each person's vote counts once. `fetchRawBill` stores related bills →
`billDiffer` keeps each bill's identical-bill link list (`BillsManifest`, `pk` `BILL_COMPANION_DECL`) →
`publishBillsManifest` (every 10 minutes) pairs a House bill with its Senate counterpart of the same congress when
either lists the other, neither has another candidate and both are in the manifest, and writes the pairs to
`BillsManifest` `pk` `BILL_COMPANION_GROUPS`, `sk` `CURRENT` (House bill first) → every reader
(`fetchBillsManifest`, `fetchProcessedBill`, `fetchBillStats`, `fetchCivicScore`, `fetchCivicProfile`,
`billStatsAggregator`, `userMatcher`, `userNotifier`, `billPriorityResolver`, the weekly digests) reads that row,
cached up to 60 s. The shared code is `src/shared/billCompanions.ts` (pure: guid parsing, link extraction, the pairing
rule, one-row-per-group helpers) and `src/adapters/billCompanionDao.ts` (the two row kinds). The switch
`COMPANION_GROUPS_ENABLED` (publisher only) decides whether pairs are published; a missing row or a row written with
the switch off means no groups, exactly the behaviour before APPF-23. The consumers other than `fetchBillsManifest`,
`fetchProcessedBill` and `publishBillsManifest` also skip companion handling when `MANIFEST_TABLE_NAME` is unset.
Votes are never moved between the bills of a pair. Operations: `../docs/RUNBOOK.md`, section 12.

## Logging and tracing a bill (OBS-10)

The bill pipeline handlers (`billsApiPoller`, `fetchRawBill`, `enrichOfficialVotes`, `billDiffer`, `billSummarizer`, `notificationType`, `userMatcher`, `notificationFanout`, `notificationDispatcher`, `userNotifier`) log through `src/shared/logger.ts`: one JSON object per line with `timestamp`, `level`, `message`, `service` (`billboard-services`), `fn` (the Lambda function name), `awsRequestId`, the correlation keys in scope (`correlationId`, `guid`, `bioguideId`, `userId` as the Cognito sub, `sqsMessageId`) and the call's own fields. Errors are written as `{ name, message, stack }`, plus `code`, `statusCode` and `cause` when present; if reading an error's `stack` throws, the line is still written, without it. Keys named like tokens, emails, addresses, passwords, secrets or request bodies are written as `[redacted]`; never put such values in a message. `LOG_LEVEL` (`debug`, `info`, `warn`, `error`; default `info`) sets the lowest level written.

**Correlation id.** `billsApiPoller` mints `<runStartedAt>:<guid>` for each bill it enqueues (`src/shared/correlation.ts`). Every producer copies it into the SQS message attribute `correlationId`. `billSummarizer` and `billDiffer` store it as the processed bill's S3 user metadata (`x-amz-meta-correlation-id`, next to the REL-30 `source-text-hash`, `source-raw-version` and `source-fetched-at`; raw bills carry the correlation id too), because the manifest and notification steps start from an S3 event; `notificationType` reads it back from the object and sends it on to `userMatcher`, which passes it to `notificationFanout` (message attribute and body); the pending notification rows keep it. `notificationDispatcher` batches users rather than bills, so it sends its own run id; `userNotifier` logs one `Bill notification outcome` line per bill with that bill's id and the run id as `dispatchCorrelationId`. A handler that receives no id (older messages, backfills) mints one.

**Follow one bill** in CloudWatch Logs Insights, with the log groups `/aws/lambda/BillsApiPoller`, `FetchRawBill`, `EnrichOfficialVotes`, `BillDiffer`, `BillSummarizer`, `CreateBillsManifest`, `NotificationType`, `UserMatcher`, `NotificationFanout`, `NotificationDispatcher` and `UserNotifier` selected:

```
fields @timestamp, fn, level, message, correlationId, outcome, reason, decidedBy, sqsMessageId, userId
| filter @message like /BILLS-119hr1234[^0-9]/
| sort @timestamp asc
| limit 10000
```

The pattern matches every version suffix of the bill (`ih`, `rh`, ...) and not `BILLS-119hr12345`. To follow one pass through the pipeline instead, filter on its id: `| filter @message like "2026-09-24T14:05:00.000Z:BILLS-119hr1234"` (the poller's `Enqueued bill` line gives it). `createBillsManifest` (between the processed-bill S3 event and `notificationType`) is not converted yet and logs only failures, which match the first query through the processed-bill key or guid.

**Where a push ended.** `userNotifier`'s `Bill notification outcome` line has `outcome` `delivered` (at least one device was sent a push carrying the row; `devicesSent` says how many), `not_sent` (no device was: no endpoint, the notification type is off, or the device got the other row of an outcome change, UX-33), `no_devices`, `held` (the user's quiet hours or the push pace, with `heldUntil` and `holdReason`; the row is sent after it, S5 and UX-33), `dropped_revoted` (an `updated` row deleted unsent because the user voted on the bill after its summary changed, UX-33), and for a row past its 24 hours (C1.3) `would_expire` (watch mode: the row is then handled as usual and also gets one of the first three) or `expired` (enforce: deleted unsent). The last two carry `ageSeconds` (from `createdAt`), `createdAt`, `ttl` and `pendingExpiryMode`; in enforce mode the warning `Deleted pending notifications past their lifetime unsent` (`userId`, `pendingKeys`) follows. In `/aws/lambda/UserNotifier`: `filter message = "Bill notification outcome" | stats count() by outcome`.

### Messages acknowledged without retry (C1.8)

Some messages can never succeed, and their consumer acknowledges them (they are not retried and never reach a DLQ). Each such drop now calls `reportUnprocessableMessage` (`src/shared/unprocessableMessages.ts`), which writes:

- one warning, `Message cannot be processed; acknowledged without retry`, with `dropSite`, `reason`, `messageId`, any site fields, and the message: `messageContent` (the parsed body, when it is JSON of at most 2 KB, so the logger's key redaction applies at any depth) or `messagePreview` (the first 256 characters otherwise; a larger JSON body is previewed with the same keys redacted);
- one embedded-metric line, `MessagesUnprocessable` = 1 in `BillBoard/Pipeline`, with no dimensions and `dropSite` and `reason` as properties. The alarm `Billboard-Pipeline-MessagesUnprocessable` fires on 1 or more in a day.

The helper never throws, needs no permission and makes no call, so every message is acknowledged exactly as before; with no drop there is no datapoint. Usual causes: an old-shape message left in a queue at a deploy, or a mistyped hand-sent one.

| `dropSite` | When | `reason` |
|---|---|---|
| `fetchRawBill.unidentifiedBill` | A feed item names no bill the handler can identify | `unparseable_link` (the `link` is logged), `no_bill_id` |
| `billDiffer.missingGuid` | A message without a bill guid | `empty_body`, `invalid_json`, `missing_guid` |
| `billSummarizer.refused` | Bedrock refused to summarize the bill twice, the second time on shortened text (LLM-11; logs `guid`, `correlationId` and the refusal `category`). Every record naming the bill is acknowledged, nothing is stored, and the bill keeps its previous summary or stays unpublished. billDiffer sends it again on each later raw write while its text is pending, so it can recur and hold the alarm in ALARM; forcing a rerun is a deliberate step (`../docs/RUNBOOK.md` 11.7) | `refusal` |
| `enrichOfficialVotes.missingGuid` | A message without a bill guid | `empty_body`, `missing_guid` |
| `enrichOfficialVotes.rawBillMissing` | No raw bill exists for the guid | `raw_bill_not_found` |
| `notificationFanout.malformed` | A fan-out chunk that can never be read | The parser's text: `body is not JSON`, `body is not an object`, `missing or invalid version`, `missing billId or billTitle`, `missing or invalid notificationType`, `missing userIds`, `no valid userIds`. A newer message `version` is not a drop: it fails and reaches `notificationFanoutDLQ` |
| `notificationType.currentMissing` | The processed bill's version cannot be loaded: the version the message names, or for a message without one the latest (logs `key` and `versionId`, not the S3 event; the record's other objects go on) | `version_not_found` (a named version, REL-59), `current_not_found` (no version named) |
| `notificationType.unresolvedBillId` | No bill id from the processed bill or its key (logs `key` and `versionId`) | `no_bill_id` |
| `userMatcher.malformed` | Not a `notificationType` message | `empty_body`, `invalid_json`, `not_notification_type` |
| `userNotifier.malformed` | A dispatcher batch that cannot be read | `empty_body`, `invalid_json`, `invalid_structure` (no `userIds` array), `no_user_ids` |

The new line replaced each site's old one, so these messages no longer appear: `Failed to identify bill from feed item` (`fetchRawBill`, which also goes from `error` to `warn`), `Skipping SQS record without a bill guid` (`billDiffer`), `Skipping malformed notification fan-out message`, `Skipping object; could not load current` and `Skipping processed bill; could not resolve id` (`notificationType`), `Skipping SQS record; expected NotificationType message` (`userMatcher`), and in `userNotifier` `Skipping SQS record with empty body`, `Invalid batch payload structure`, `Batch payload contained no valid user IDs` and `Failed to parse SQS record body as JSON`. Not counted (unchanged): a body that is not JSON in `fetchRawBill` or `enrichOfficialVotes` is still retried and reaches the DLQ, and `userMatcher` still acknowledges "Processed bill not found for notificationType" without counting it.

Every drop in the chosen time range, with the log groups of those eight functions selected:

```
fields @timestamp, fn, dropSite, reason, messageId
| filter message = "Message cannot be processed; acknowledged without retry"
| stats count() by fn, dropSite, reason
```

## Bedrock calls (LLM-11)

`billSummarizer` and `billPriorityResolver` call Claude on Amazon Bedrock (`InvokeModel`, Anthropic Messages format)
through `src/shared/bedrockMessages.ts`, which the eval and probe scripts use too:

- `requestProfileForModel` reads the model from `MODEL_ID` (a model ID, inference profile ID or ARN) at cold start:
  `haiku-4-5` or `haiku-5-5`; any other model throws. `modelRequestFields` adds what differs by model: `temperature: 0`
  on Haiku 4.5 (the summarizer only), and `output_config.effort` on Haiku 5.5 unless the effort is `default`. No
  request sends `thinking`, `top_p`, `top_k`, `fallbacks`, tools or `output_config.format`, and none ends with an
  assistant turn.
- `readMessagesResponse` reads `stop_reason` before the content: `ok` (`end_turn`, `stop_sequence` or none),
  `refusal`, `max_tokens` or `incomplete`. A refusal's text is always empty, so nothing from a refused answer is used.
  The text is every `text` block joined; thinking blocks, which Haiku 5.5 sends first, are counted and skipped.
- `invokeMessages` makes one call. The client makes one attempt per send (`createBedrockClient`); `invokeMessages`
  retries throttles up to `BEDROCK_MAX_RETRIES` times, transient errors (5xx, 424, `ModelNotReadyException`, network
  errors, including the HTTP/2 client's reset or refused streams) twice and a `ModelTimeoutException` once, with
  backoff, and only while the invocation has `BEDROCK_MIN_REMAINING_MS` left. Each attempt is aborted at
  `BEDROCK_CALL_TIMEOUT_MS`, or 5 s before the invocation would end if that is sooner. A rejected request (400, 403,
  404) and its own deadline are never retried. It resolves with every answer, refusals and `max_tokens` included, and
  throws `BedrockCallError` (`kind`, `errorName`, `httpStatus`) when no answer came back.

| Variable | Infra value (summarizer, resolver) | Unset |
|---|---|---|
| `MODEL_ID` | The ARN of the caller's `us.` inference profile (`infra/lib/config/bedrock-models.ts`; Haiku 4.5 for both) | Fails at cold start, as does a model with no request profile |
| `BEDROCK_EFFORT` | `medium`, `low` | The same values. Anything but `low`, `medium`, `high` or `default` fails at cold start |
| `MAX_OUTPUT_TOKENS` | `8192`, `4096` (thinking counts toward it on Haiku 5.5) | The summarizer fails; the resolver uses `4096` |
| `MAX_BILLS_PER_BATCH` (summarizer) | `1` | Fails |
| `BEDROCK_CONCURRENCY` (summarizer) | `3`: calls one invocation runs at once | `1` |
| `BEDROCK_CALL_TIMEOUT_MS` | `60000`, `75000` | The same values |
| `BEDROCK_MIN_REMAINING_MS`, `BEDROCK_MAX_RETRIES`, `BEDROCK_BASE_DELAY_MS`, `BEDROCK_MAX_DELAY_MS` | Not set | `20000`, `4`, `1000`, `15000` |

**What they log and count.** Each attempt writes one `bedrock_call` line: `caller`, `kind`, `attempt`, `outcome`,
`modelId`, `requestProfile`, `effort` (what was sent, so null on Haiku 4.5) and `max_tokens`; with an answer also
`stop_reason`, `refusal_category`, `content_types`, `thinking_blocks`, `text_chars`, the token counts and `latencyMs`;
with an error `errorName`, `httpStatus` and `errorMessage`. It also writes embedded metrics in `BillBoard/Bedrock`:
`BedrockCalls`, `BedrockLatency` and `BedrockOutputTokens` by `Caller` and `Outcome`, and, with no dimensions,
`BedrockRequestRejected` (400, 403 or 404), `BedrockThrottled` and `BedrockRefusal`. The outcomes, the alarms and the
queries are in `../docs/RUNBOOK.md` 11.7.

`billSummarizer` keeps the display limits (title 100 characters; soWhat 280 characters and 2 sentences; each breakdown
field 400), and its prompt asks for 80, 240 and 300. Per bill, with `guid` and `correlationId`, it logs
`analysis_rejected` (an answer broke a rule: `attempt`, `errors`, `issues` with each field's text, `correctiveRetry`),
`analysis_revised`, `analysis_repaired` (each fitted field's `rules`, `method` and `original` text),
`summary_refused`, `summary_from_reduced_input`, and for every stored summary `summary_stored`, the provenance record
(`modelId`, `requestProfile`, `effort`, `calls`, `revised`, `reducedInput`, `repairedFields`, `civicAxes`, the number
of civic axes stored (0: no civic profile, REL-43), and each field's characters and sentences). In
`BillBoard/BillIngestion` it counts `BillSummarizerStored`, `BillSummarizerAnalysisRevised`,
`BillSummarizerRepairedBills` and `BillSummarizerFieldRepaired` per stored bill, and `BillSummarizerAnalysisRejected`,
the answers it rejected.

`billPriorityResolver` logs `priority_request` (`now`, `maxResults` and the `payload` its prompt embeds: public
headlines and bill titles) and `priority_no_answer` (`reason` `refusal`, `max_tokens`, `incomplete`, `empty` or
`unparseable`; `stop_reason`, `refusalCategory`, `output_tokens`, and a 300-character `preview` when unparseable), and
counts `PriorityResolverNoAnswer` in `BillBoard/Bedrock`. For an answer it can use it logs `priority_answer` instead:
`candidatesSent`, `billsReturned`, `billsPassing` (the bills that pass the thresholds), `billsActivated`,
`activatedGuids`, `newPicks` and `newPickGuids` (REL-51: the activated bills not in the news when the run started),
`topScore`, `topConfidence`, `answerEmpty`, `minScore` and `minConfidence`, numbers and guids with no titles or reasons.
It counts `PriorityAnswerBills`, `PriorityPassingBills`, `PriorityNewPicks`, `PriorityTopScore` and
`PriorityTopConfidence` in `BillBoard/Bedrock` (the last two not for an answer of no bills), and `PriorityInputTokens`
for each answered call. Before the call it logs `priority_candidates` (the title lookups, the resolutions left out,
the candidates by type and how headlines named them). `docs/RUNBOOK.md` 11.7 and 22 have the Logs Insights queries and
how to read them.
